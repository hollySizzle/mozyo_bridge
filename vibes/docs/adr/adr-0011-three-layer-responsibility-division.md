## 決定 (規約行)

3階層構造は **「どの役割がどの決定に責任を持つか」の責務分担** である。**同じものを役割間で再レビューさせない** — 多重レビューは伝言ゲームで精度が落ち、決定事項 (ADR) を骨抜きにするため禁止する。各役割は下記の責務を持つ。**ADR は全役割で参照必須**とし、どの役割も ADR に反する判断をしない。

## 各役割の責務

### サブレーン (実装役 + 別モデル系統レビュー役)

- 1つのユーザーストーリー (US) を git worktree 内で実装する。
- **その US の監査もここで完結する** — コードレビューも US 監査もサブレーン。US の正しさを保証する検査はここ1回であり、**上位に再捕捉の網は置かない (意図的)**。
- レビュー役は実装役と**別モデル系統**でなければならない (系統を跨ぐ敵対的多様性が唯一の網であるため)。

### プロジェクトコーディネーター (Redmine Version 単位)

**用語**: ここでいう「バージョン」は **Redmine Version = 計画・スコープのグルーピングの器** (どの仕事を束ねるか) であり、**パッケージのリリース版番号ではない**。リリースの版番号は release gate / tag 時点で別途決める (repo 規約: 各 Redmine Version 説明の「パッケージ版番号ではない」、および #270 roadmap metadata cleanup)。したがってプロジェクトコーディネーターが「持つ」のはスコープの器であって、出す版番号ではない。

その Redmine Version (スコープの器) の責務。**検証語ではなく決定語で定義する** (「確認/検証」の語はサブレーンで済んだ正しさの再レビューを招くため使わない)。

- **サブレーンを終端まで drain する (最重要責務)**: dispatch したサブレーンを、**統合 + close + worktree/pane 撤去まで、または明示的に retire するまで、必ず終端状態へ持っていく**。**中途半端に実装したまま終端させず放置されたサブレーンの滞留が最悪の失敗**であり (owner 明確化 #15631 j#109280)、その発生を防ぎ回収する責任がプロジェクトコーディネーターにある。Version 配下の未 close issue / 未 drain サブレーンの氾濫はプロジェクトコーディネーターの責務 (owner 明確化 #15631 j#109265)。dispatch と drain が対で、**力点は drain 側**。(Version close の機械化は #15822 が前提。未整備の間は issue 単位 close の手動確認で代替。)
- **サブレーンを dispatch する**: このバージョンの各 US をサブレーンへ実際に dispatch する。範囲・順序を決めるだけでなく **dispatch の実行そのもの**をプロジェクトコーディネーターが持つ (owner 明確化 #15631 j#109265 / j#109280)。dispatch は drain と対の責務であり、起こしたものは必ず終端させる。
- **範囲を決める**: このバージョンにどの US を入れる/入れないか、US 同士の境界 (重複も欠落もしないように)。
- **順序を決める**: サブレーンに何から着手させるか。
- **進め方を決める (proportionality)**: 指摘を今やる価値がない→やらない / やりすぎ→今はやめる。
- **衝突を解決する**: 2つの US が同じ所を触って競合したとき、どちらに寄せるかを**決める** (これは判断であってレビューではない)。
- **統合の健全性は「統合後のテストが緑か」という機械的信号に委ねる**。人/エージェントが各 US を主観で再レビューしない。

**明記**: プロジェクトコーディネーターの統合責務は「判断」と「機械的テスト」に限り、**主観的な再レビューを含まない**。「バージョンとして問題ないかの最終確認」という検証語は本 ADR では採らない (再レビューを招くため)。統合バグ (US 単体では壊れないが統合すると壊れる) の持ち主はプロジェクトコーディネーターだが、その検出は統合テスト (機械) と衝突解決 (判断) が担い、各 US の再監査ではない。

### コーディネーター

- 複数の Redmine Version (スコープの器) に束ねた**仕事を取りまとめ、それをリリースに値するか・そのリリースに価値があるか** (プロダクトの価値判断) を決める。**リリースは Redmine Version とは別の行為**であり、実際の版番号は release gate / tag 時点で決める (Redmine Version 名 = 出す版番号ではない)。コーディネーターが判断するのは「束ねた仕事をリリースとして切るか」であって、器の名前を版番号として採用することではない。
- **リリースはコーディネーターの責務**: バージョンが統合されたのにリリースされていない状態はコーディネーターの責務である (owner 明確化 #15631 j#109265)。統合 (プロジェクトコーディネーター) の後段でリリースが滞ることをコーディネーターが持つ。
- owner との対話窓口、意思決定の捕捉 (ADR)、owner 承認の収集、最終クローズ可否。

## 原則: なぜ多重レビューを禁止するか

- 各役割に同じ正しさを再確認させると、**伝言ゲームで精度が落ちる** (relay 劣化)。
- 上位が下位の判断を"念のため"上書きできる構造は、**決定事項 (ADR) を骨抜きにする**。
- したがって「上位で新しい観点を見る (例: プロジェクトコーディネーターの US 統合、US 単体では見えない結合問題)」は正当だが、「上位で同じものを再レビューする」は禁止する。前者は新しい scope、後者は劣化。

## 正直なトレードオフ (本 ADR は rosy な文書ではない)

1. **サブレーンのレビューが唯一の網**: US の正しさを保証する検査がサブレーン1回になり、上位に再捕捉が無い (意図的)。ゆえに**サブレーンのレビュー役の系統独立性が load-bearing** であり、サブレーンの対が死角を共有すると誰も気づかない。冗長を削る設計は正しいが、その分だけサブレーンの品質と、レビュー結果を上へ返す**返送経路の堅牢性**に賭けている。(現状更新 2026-08-19: 返送シナリオの isolation 結合不安定は #15709 で、callback 不達 3 class (precondition_not_idle 死蔵 / lane_binding_absent / receiver 導出) は #15707 で、suite の ambient home / 実 remote SSH coupling は #15711 で解消済み。残る既知穴は L2→L1 default-lane callback の `target_unavailable` (受信側 terminal generation 証明不足) で #15712 が追跡中。不達時も durable-record polling で運用は成立している。)

2. **プロジェクトコーディネーターが空席だと owner がボトルネックになる**: 「finding を飛ばすか/やりすぎか」の proportionality 判断はプロジェクトコーディネーターの責務だが、その判断が owner 本人に上がる構造は owner をボトルネックにする。プロジェクトコーディネーターを担い手 (レーン) で埋めるのが owner を外す最大のテコであり、本モデルの実効性はプロジェクトコーディネーターの staffing とセットで初めて出る。(現状更新 2026-08-20: #15693 の bounded trial で L2 lane (`issue_15693_l2_r2`, delegated_coordinator) が稼働。charter (#15693 j#109253) 下で L2 が **サブレーンを自律 dispatch** (#15816 の L3 lane 新規作成 + 通知)・既存 lane coordination の adopt・設計相談の一次 Answer・state-only uptake を実行できることを実証 (#15693 j#109262)。これは本 ADR がプロジェクトコーディネーターの最重要責務とする「サブレーン dispatch」の live 実証である。常設化の owner 判断は未収集で #15693 を open anchor として維持。)

3. **「ADR 全役割参照」は機構が要る**: 各役割の文脈へ ADR を実際に注入・解決する仕組み (既存の role_profile / workflow_contract 注入の延長) が無いと「参照必須」が掛け声で終わる。これはハーネス整備項目 (#15631 後続)。

## モデル配置 (原則と正本の分離)

本 ADR が規定するのは**配置の原則のみ**とする: (a) サブレーンのレビュー役は実装役と別モデル系統であること、(b) coordinator 席と review 系統の独立が保たれること。**具体の provider / model 値は本 ADR に書かない** — 正本は committed `.mozyo-bridge/config.yaml` (`agents.profiles` / `provider_binding`、設計正本 #13157) であり、運用切替は config commit + Redmine 記録で表現する (router 規約と同じ向き)。ADR に具体値を焼き込むと owner の配置変更のたびに ADR が古くなるため、これは初稿 (2026-08-18 朝時点の「L1=Codex X-High / 補佐=Fable5」焼き込み) からの**構造修正**である。

変遷の記録 (事実、正本は各 Redmine anchor): 2026-08-18 朝に L1=Codex X-High トライアル → 同日 owner 指示で **L1 coordinator = Claude 系 / coordination assistant = Codex X-High** へ rebind (#15655)。2026-08-19 owner 指示で **サブレーン実装 worker = Opus 5 (Claude 系)** へ切替 (#15631 j#108184)。プロジェクトコーディネーター (delegated coordinator) とサブレーンの review gateway は Codex 系 — したがって「実装 = Claude 系 / review = Codex 系」の系統独立 (原則 a) は全変遷を通じて維持されている。ADR-0009 draft の「coordinator = Claude 系統」との関係は rebind 後は整合に戻っており、ADR-0009 最終化時に本節と照合する。

## 影響

- 3階層で実装するときの責務は本 ADR に従う。多重レビューを足す変更、およびプロジェクトコーディネーターに主観的再レビューを持ち込む変更は本 ADR と矛盾する。
- 本モデルの実効化は「プロジェクトコーディネーターの staffing」「サブレーン返送経路の堅牢化」「ADR 注入機構」を前提とし、これらは #15631 で分解・追跡する。(現状 2026-08-19: 前2者は上記トレードオフ節の現状更新のとおり実質達成、ADR 注入機構は未着手のハーネス整備項目のまま。)
- 成功条件は「全機構を作り込んで production-ready 宣言」ではなく、**最小の3階層 (プロジェクトコーディネーター1人 + サブレーン1対) で実在の1 US を最後まで通す**こと。**この成功条件は 2026-08-19 に完全形で達成された** (判定 anchor: #15631 j#108127、実証 US #15703。以後 #15709 / #15710 / #15711 でも同型で再現)。達成は「モデルが実運用可能」の実証であり、本 ADR の ratify (文面裁定) は別途 owner の行為として残る。
- status は proposed。owner の文面裁定 anchor が成立するまで active な ADR として扱わない。適用範囲は本 repo (repo-local 宣言)。中央 preset / OSS 配布物は本 ADR では変更しない。
