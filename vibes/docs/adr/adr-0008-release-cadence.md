# ADR-0008: リリースは早く小さく出す。現段階の cadence は半日に 1 回を上限、1 日複数回はしない

- status: active
- date: 2026-08-17
- related: Redmine #15594 j#106992 (owner 決定の逐語記録)、`vibes/docs/rules/release-distribution.md`、ADR-0003 (release/version/US 粒度)、ADR-0007 (2.0 scope)

## 決定 (規約行)

リリースは **早く小さく出す** (dogfooding でバグを早期検出) を基本方針とする。ただし細かすぎる
リリースは all-test / リリース前検証を過重にするため、**1 日に複数回はしない**。現段階の cadence
は **半日に 1 回を上限**、最低ラインは **2〜3 日に 1 回**、agent が 24h 稼働なら理想は 1 日 1 回。
半日より細かい cadence は採らない。cadence は LLM 精度と変更規模に依存し、製品成熟で軽微変更中心
になれば細かく見直してよい。

## 背景

2.0 を細かく切って早く出す方針 (ADR-0007) を採るにあたり、「どのくらい細かく切ってよいか」の
上下限を owner が定めた。dogfooding の利益 (早く出すほどバグが実運用で早く見つかる) と、
リリース前の全テスト・検証コストの増大 (1 日に何度も回すと重い) のトレードオフを、現段階の
LLM 精度と変更規模を前提に固定する。

## 根拠 (逐語引用)

出所: #15594 j#106992 (owner 決定の逐語記録、2026-08-17 chat)。

- 「ただし、あまりにも細かすぎると、今度はオールテストがすごく複雑になるか、リリース前の
  テストがすげえ重くなっちゃうので、1 日に何度もリリースするというのはやるべきではないと
  思います。最低でもこのペースでやるんだったら、2、3 日に 1 回はしたいです。」
- 「できればこのぐらいのペースで、24 時間あなたが動き回っているのであれば、1 日に 1 回ぐらいは
  リリースした方がいいと思います。最初は半日に 1 回くらいがいいかな。半日よりもさらに細かく
  しすぎると、あまり良くないかなと思います。」
- 「この辺は LLM の精度にもよってくるし、変更の多いリリースかどうかにもよってきます。だんだん
  このプロダクトが成熟してくれば、リリースは軽微な変更になっていくだろうから、細かくやって
  いってもいいと思いますが、今はそれぐらいがいいかなと思っています。」

## 影響

- **release gate / publish の頻度規約**: 1 日複数回の release は行わない。現段階の目安は半日に
  1 回を上限、2〜3 日に 1 回を下限とする。この window 内で「早く小さく」を優先する。
- **半日より細かい release を計画しない。** 細分化の誘惑 (1 変更 1 release 等) は本 ADR で抑える。
- **再評価条件**: LLM 精度の向上、または製品成熟による変更の軽微化。そのとき cadence を細かく
  見直してよいが、見直しは owner 裁定 (本 ADR の supersede) を要する。現段階の値は上記で固定。
- 本 ADR は release の**頻度**方針であり、release gate の**手順** (approval / Trusted Publishing /
  fresh install smoke 等、正本 `release-distribution.md`) は変更しない。
- 本 ADR と矛盾する「1 日に複数回 release する」運用は `adr_conflict_gate` の対象。
